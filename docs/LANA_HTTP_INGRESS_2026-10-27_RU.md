# Лана — защита локального HTTP-входа, 27.10.2026

## План и критерии готовности
Проверить серверный HTTP-мост из PR #53 и устранить конкретные причины зависания/падения при некорректных входящих запросах. Критерии: (1) частично присланный POST завершается за конечное время; (2) повторяющийся Content-Length отклоняется; (3) огромный десятичный Content-Length отклоняется **до** преобразования в int; (4) обычные безопасные запросы продолжают работать; (5) полный Python CI и Android CI остаются зелёными.

## Обнаруженные причины
1. `ThreadingHTTPServer` читал `rfile.read(Content-Length)` без сетевого тайм-аута. Клиент мог отправить заголовки и один байт, а затем держать поток бесконечно. Это не относится к реальной HTTPS-сессии на планшете, но создаёт риск для локального сервера за прокси.
2. Заголовок `Content-Length` разбирался через `int(...)` без ограничения длины. Очень длинная десятичная строка могла вызвать `ValueError` ещё до ответа HTTP.
3. Повторные заголовки Content-Length не отклонялись явно; перед прокси это нежелательная неоднозначность.

## Исправление
- На уровне каждого соединения задан предел ожидания входящих байтов 15 секунд. При неполном POST — HTTP 408 и закрытие соединения.
- Дубликаты Content-Length → HTTP 400; отсутствующий → HTTP 411; недопустимый/слишком большой → 411/413.
- Не изменены маршруты, токены, разрешённые типы задач, OpenAI-клиент, схема SQLite, приложение и инфраструктура.
- Добавлены независимые loopback-тесты для всех четырёх сценариев.
