# LANA — контроль доступа ко ВСЕМ HTTPS-маршрутам (29.10.2026)

## Причина
Предыдущая проверка PR #55 требовала HTTP 401 без токена только от `/v1/status`. Если reverse proxy ошибочно открыл `/v1/connections` всем, предыдущая проверка всё равно могла пройти. Это реальный пробел в тестовой приёмке; факта такой ошибки на рабочем сервере **нет**.

## План и критерии
1. Проверить **оба** GET-маршрута без токена: `/v1/status` и `/v1/connections`. Каждый обязан ответить 401.
2. Только после двух успешных отказов отправлять токен на оба маршрута и проверять JSON-схемы.
3. При публичном `/v1/connections`, 403 вместо 401, редиректе, TLS-ошибке, некорректном JSON, слишком большом ответе — остановиться; не посылать токен.
4. Независимо проверить GitHub Actions: серверные тесты, сборки и эмуляторы, не выдавать CI за живую проверку VM.
5. Никаких POST, вызовов OpenAI, реальных ключей, деплоя, изменений Android и сделок.

## Цикл и журнал
- База: `test/lana-https-auth-acceptance-20261028`, PR #55, последний подтверждённый CI 28.10: 76 серверных тестов и 4 Android workflow SUCCESS.
- Изменение: добавлена независимая проверка `/v1/connections` без токена, теперь **4 GET** вместо 3.
- Добавлены регрессии: ошибочно публичный маршрут и 403 вместо ожидаемого 401, с подтверждением, что ни один токен ещё не передавался.
- **Точка продолжения:** дождаться независимых CI на новой ветке; при ошибке разобрать лог, исправить, повторить. При пяти одинаковых ошибках пересмотреть подход.
- Откат: не объединять draft PR. Main, VM и установленная Лана остаются неизменными.

## Ограничения
Успешный mock/локальный TLS не доказывает, что настоящий сервер настроен безопасно; отдельная проверка на изолированном staging требует согласованного адреса и временного токена, который нельзя коммитить. Настоящий голос, TTS, память после сбоя и режим 24/7 не проверяются этим этапом.

## Готовность
Голосовая Лана ≈60%, автономная Лана 24/7 ≈30%. Увеличение процента только после функциональной приёмки, не по числу тестов.
